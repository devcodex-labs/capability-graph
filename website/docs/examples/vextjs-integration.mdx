# VextJS 集成

<span className="cg-status">有前置条件的可运行源码示例；固定来源实测</span>

仓库提供 examples/vextjs/ 的官方文档导出器、原生 MCP 审计工具、stdio 客户端。默认回归验证接入合同；真实验证需要固定的 VextJS 安装快照及仓库外验证项目。它们是源码示例，不属于 Core 的 npm 导出。Core 继续保持框架无关。

## 首次接入：官方文档 Provider

这条路径只需要 Git、Node.js 和 npm，不需要 MCP、Redis 或 MongoDB。先按[安装页](../getting-started/installation)将 Core **2.0.0** 安装到独立的 `capability-graph-demo/`，并保留本仓库源码 `source/`；两者位于同一工作目录。以下脚本依赖仓库中的导出器，不能只安装 Core 就导出 VextJS 文档。

本例固定 VextJS 提交为 `ef926649926e17543562b8169982fa1786285ecf`。它的版本文本为 2.0.0，但与 npm `vextjs@2.0.0` 不同：发布包没有原生 `mcp` 命令，也不含完整官网目录。先用这个确切源码验证，之后再单独验证你选择的版本。框架构建推荐 Node 20.19.0 或 24.19.0；Windows Node 22 使用 22.23.3，该框架在 Windows 22.12.0 的文件身份检查失败，具体证据见页末。

终端进入 Core 源码 `source/`，取得并构建同级固定框架：

```sh
git init ../vextjs-fixed
git -C ../vextjs-fixed remote add origin https://github.com/devcodex-labs/vextjs.git
git -C ../vextjs-fixed fetch --depth=1 origin ef926649926e17543562b8169982fa1786285ecf
git -C ../vextjs-fixed checkout --detach FETCH_HEAD
npm ci --ignore-scripts --prefix ../vextjs-fixed
npm --prefix ../vextjs-fixed run build
cd ../capability-graph-demo
```

在消费项目创建 `export-vextjs.mjs`。导出器核验完整提交、构建指纹及逐篇 Git blob，输出新的 `providers/vextjs/`；目录已经存在时会拒绝覆盖。

```js title="export-vextjs.mjs"
import path from 'node:path';
import { mkdir } from 'node:fs/promises';
import { pathToFileURL } from 'node:url';

const [coreSource, frameworkSource] = process.argv.slice(2);
if (!coreSource || !frameworkSource) throw new Error('需要 Core 源码和固定 VextJS 源码两个目录');
const repositoryRoot = path.resolve(coreSource);
const sourceRoot = path.resolve(frameworkSource);
const { verifyVextSource } = await import(pathToFileURL(path.join(repositoryRoot, 'examples/vextjs/source-provenance.mjs')).href);
const { exportVextProvider } = await import(pathToFileURL(path.join(repositoryRoot, 'examples/vextjs/documentation-provider.mjs')).href);
const source = await verifyVextSource({ frameworkRoot: sourceRoot, sourceRoot,
  sourceIdentity: 'ef926649926e17543562b8169982fa1786285ecf' });
await mkdir(path.resolve('providers'), { recursive: true });
const exported = await exportVextProvider({ providerId: 'vextjs', version: source.version,
  source, sourceRoot, repositoryRoot, outputDir: path.resolve('providers/vextjs') });
console.log(JSON.stringify({ rootDir: exported.rootDir, capabilities: exported.count,
  documents: exported.documentCount, commit: source.commit }));
```

再创建 `discover-vextjs.mjs`，从实际安装的 Core 根入口注册 directory Provider、发现目录并分页读回路由指南：

```js title="discover-vextjs.mjs"
import { createHash } from 'node:crypto';
import path from 'node:path';
import { CapabilityGraph } from '@devcodex/capability-graph';

const graph = await CapabilityGraph.open({
  hostAllowedProviders: ['vextjs'], integrationEnabledProviders: ['vextjs'],
  providers: [{ providerId: 'vextjs', authority: { kind: 'file', definitionLayout: 'directory',
    rootDir: path.resolve('providers/vextjs') } }],
});
try {
  const provider = graph.forProvider('vextjs');
  const catalog = await provider.listCatalog({ limit: 20 });
  const requiredStaticRevision = catalog.meta.staticRevision;
  const detail = await provider.getCapabilities(['routing'], { requiredStaticRevision });
  const routing = detail.results[0];
  if (!routing?.ok) throw new Error('routing 能力读取失败');
  let cursor;
  let firstPage;
  let text = '';
  let pages = 0;
  do {
    const page = await provider.readDocumentPage({ capabilityId: 'routing', knowledgeId: 'guide.routing',
      maxBytes: 4096, requiredStaticRevision, ...(cursor ? { cursor } : {}) });
    firstPage ??= page;
    text += page.text; pages++; cursor = page.nextCursor;
  } while (cursor);
  console.log(JSON.stringify({ catalog: { count: catalog.items.length, hasMore: Boolean(catalog.nextCursor) },
    capabilityId: routing.value.id.capabilityId,
    document: { pages, totalBytes: Buffer.byteLength(text), sha256: createHash('sha256').update(text).digest('hex'),
      contentId: firstPage.contentId, source: firstPage.source, firstPageHasMore: firstPage.hasMore,
      fullyRead: !cursor, preview: firstPage.text.slice(0, 160) } }));
} finally { await graph.close(); }
```

执行：

```sh
node export-vextjs.mjs ../source ../vextjs-fixed
node discover-vextjs.mjs
```

第一条应输出 46 个能力、91 篇文档和上述完整提交；第二条应输出 `routing`、`knowledge/guide/routing.md`、连续分页后的总字节和哈希。Catalog 这里只查第一页，有续页不等于全部能力。示例循环为验证原文完整性而续读全文；Agent 可按需要停止或选择范围。仓库目录名称不同，只需调整第一条的 Core 源码参数。

这个导出结果可交给你自己的 API/MCP；远程正文按 [KnowledgeReader 接入](../integrations/knowledge-reader)配置读取器。下面的来源矩阵用于核验原文和图谱，正文搜索由独立模块负责。

## 来源与角色

面向接入的 Provider 按官方文档主题定义 routing、validation、plugins、database 等能力。capabilities/ 使用 JSON 定义，knowledge/ 按官方 guide/api/frontend/specification 等层级保存原始 Markdown/MDX；metadata/source-manifest.json 保存来源和章节清单，metadata/native-id-map.json 保存原生身份关联。章节关联由集成作者维护，一项能力可以读取多个指南、API 和规范，不按每个页面机械生成一项能力。

固定快照共 91 篇文档，关联到 46 个主题能力；5 篇导航或资源材料明确列为 reference-only。清单记录每篇文档的归属、哈希和验证范围。新增未分类章节或必需章节缺失会阻止导出。原文可读取不代表其中全部功能已经执行验证。

官方文档入口核对全部原文字节、正文分页还原和全部主题的静态图谱查询。安装消费者验证本地、安装包及 HTTPS 的真实来源。

原生 MCP 的 capability、rule、recipe、knowledge、workflow 在独立审计中保留 ID、status、正文、catalog digest 和来源身份。该验证目录的 native.c03 等 ID 不进入公开文档 Provider；正文按原字节保存为 Markdown，机器目录与来源信息存入 metadata/。vext:// 仅是原生来源引用，不是内核支持的 URI Reader。

原生 MCP 缺少分页枚举全部 knowledge 的资源。本例从固定安装快照的目录模块获取发现材料，再核对原生 MCP 的身份、摘要与正文。这个边界只对已核验的 schema 2 成立。`relatedIds` 是可选上下文，不据此推导 requires；原生 Recipe 的 available 也不表示 Core 会执行任务。

同来源重新导出内容稳定；来源更新后重新导出并 reload，重新查询目录及文档引用。不能只用 package.version 固定来源：VextJS main 的固定提交与 npm 2.0.0 虽然版本文本相同，目录与依赖可能不同。

## 多来源与正文出处

knowledge/ 是本例落地官方原文的约定。文件 locator 还支持其他获准本地目录、实际安装包；远程文档使用 HTTP locator 和显式配置的 Reader。每个 Provider 可以组合多种来源，不必把所有来源复制到 knowledge/。

| 材料 | 正文出处 | 读取方式 |
|---|---|---|
| knowledge/guide/routing.md 等落地章节 | 固定源码 website/docs/zh/ 的完整原始 Markdown/MDX；复制前后逐字节一致 | 默认 Provider 根内的 relative-file |
| 外部官方站点章节 | 固定源码 website/docs/zh/ 的原始文档 | relative-file，绑定 knowledgeRoots.official 目录 |
| 独立原生 MCP 审计 | 固定 schema 2 的回读正文；机器字段单独存储 | verification/native-mcp/ 中的独立验证 Provider |
| 安装包 README、CHANGELOG、MIGRATION | 实际 `node_modules/vextjs/` 或 `node_modules/monsqlize/` 中的原文 | relative-file，绑定 package 类型知识根；也可显式绑定已安装目录 |
| 固定公开 URL | 带完整提交 SHA 的官方 raw URL，正文与同提交本地文件逐字节比较 | HTTP locator，配置宿主 Reader |

knowledge/ 只存文档正文；JSON 用于能力定义和来源元数据。原生简短介绍不替代完整官方章节，章节关联不冒称 VextJS 官方声明。合同测试中的受控 Fixture 用来验证边界，不能充当官方正文或真实框架证据。旧验证项目保留历史结构，重新运行入口生成新的文档结构。

定位字段分别类似 `{"type":"relative-file","path":"knowledge/guide/routing.md"}`、`{"type":"relative-file","root":"official","path":"website/docs/zh/api/config.md"}`、`{"type":"relative-file","root":"installed","path":"MIGRATION.md"}` 和 `{"type":"http","url":"https://raw.githubusercontent.com/devcodex-labs/vextjs/固定提交SHA/website/docs/zh/api/config.md"}`。这些是 locator 字段示意；official、installed 须由接入方在该 Provider 的 knowledgeRoots 中显式绑定，URL 中的占位 SHA 必须替换。

VextJS 与 MonSQLize 分别注册独立 Provider，即使本地 capabilityId、knowledgeId 相同，也按 Provider 隔离。只有启用 directory 布局时，定义才从 `capabilities/**/*.json` 收集；知识来源不因此受限于某个目录名称。

## 保留范围的验证

先构建根包和测试示例，再运行固定来源文档校验：

```sh
npm run build
npm run build:tests
node scripts/validation/vextjs-documentation.mjs ../vextjs-fixed ef926649926e17543562b8169982fa1786285ecf
node scripts/validation/vextjs-consumer.mjs ../vextjs-fixed ef926649926e17543562b8169982fa1786285ecf --https
```

第二条验证入口创建全新的仓库外消费者，实际安装当前 Core 与固定 VextJS tarball，并安装锁定的 MonSQLize 包。验证 46 个主题的图谱查询、91 篇原始文档、目录/node_modules/HTTPS 来源矩阵、跨 Provider 隔离、正文分页与 reload。原生 MCP 仅用于声明与来源审计。

能力主题及文档关联由集成作者维护；knowledge 保存逐篇 Git blob 核验的官方原始 Markdown/MDX，来源与 SHA-256 记录在 metadata。文档读取证明原文与映射，不代表框架所有功能执行通过或 Agent 成功率。2.0 不维护检索任务、运行快照、MongoDB 应用或 Session 业务验收门禁。

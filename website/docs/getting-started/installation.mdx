# 安装

<span className="cg-status">本文对应 2.0.0 源码接口</span>

后续教程使用 2.0.0 的文件静态图谱与文档读取接口。先查询这个确切版本是否已发布，再安装；Registry 的实际结果决定包是否可用。1.x 的接口范围与本版不同，无版本安装取得的 latest 也可能与本文不同。

发布版直接安装即可；若确切版本返回 `E404`，使用下方固定源码回退。网络、认证或镜像错误需先排查，不能据此判断版本未发布。首次发现只需两个 JSON 和一个脚本。

把包装在负责加载 Provider、向 Agent 提供 API/MCP 的 Node.js 接入项目中。Provider 定义目录只是数据目录，不必单独安装一份包；一个接入项目可以加载多个 Provider。

## 前置条件

- Node.js `^20.19.0 || >=22.12.0`，与包内 `engines.node` 完全一致。
- 使用 ESM。公开入口为包根、`/mcp`、`/mcp/server`、`/readers/http`；不提供 CommonJS `require()` 入口。
- 后续将创建 Provider 定义文件；安装命令本身不会生成它们。

## 安装对应版本

在你的 Node.js 接入项目运行：

```sh
npm view @devcodex/capability-graph@2.0.0 version
npm install @devcodex/capability-graph@2.0.0
npm ls @devcodex/capability-graph
```

查询与实际安装都应显示 `2.0.0`。如果该版本尚未发布，第一条会返回 `E404`；此时不要用旧版本继续新版教程。

## 未发布时从固定源码构建

以下命令从新的工作目录开始，需要 Git、npm 和上述 Node.js。先在 GitHub 的提交页面取得**与正在阅读的文档一致的完整 40 位提交 SHA**，替换下方 `DOCUMENTATION_COMMIT`；不要使用会移动的分支名。已构建站点也可在 `release.json` 的 `documentationCommit` 查看文档提交，同时核对 `packageVersion`。`source/` 是源码，`packages/` 保存安装包，`capability-graph-demo/` 是独立接入项目。

```sh
mkdir capability-graph-preview
cd capability-graph-preview
git init source
git -C source remote add origin https://github.com/devcodex-labs/capability-graph.git
git -C source fetch --depth=1 origin DOCUMENTATION_COMMIT
git -C source checkout --detach FETCH_HEAD
cd source
node -e "if(require('./package.json').version !== '2.0.0') throw new Error('源码与文档版本不一致')"
npm ci
npm run build
mkdir ../packages
npm pack --ignore-scripts --pack-destination ../packages --json > ../packages/pack.json
cd ..
mkdir capability-graph-demo
cd capability-graph-demo
npm init -y
npm pkg set type=module
node -e "const {execFileSync}=require('node:child_process');const [p]=require('../packages/pack.json');execFileSync(process.platform==='win32'?'npm.cmd':'npm',['install','../packages/'+p.filename],{stdio:'inherit',shell:process.platform==='win32'})"
npm ls @devcodex/capability-graph
```

打包与消费目录都位于源码仓库外；安装文件名取自本次 `npm pack` 的结果。最后一条应显示 `@devcodex/capability-graph@2.0.0`。以后在消费项目根完成[第一次发现](./first-provider)。

已有项目安装上面生成的 tgz 即可，并确认模块配置。`npm pkg set type=module` 会在 `package.json` 写入 `"type": "module"`，让 `.js` 使用 ESM；已有 CommonJS 项目可以把接入脚本命名为 `.mjs`，无需改变整个项目的模块规则。

## 验证包入口

在项目根创建 `check.mjs`：

```js title="check.mjs"
import { CapabilityGraph } from '@devcodex/capability-graph';

if (typeof CapabilityGraph.prototype.readDocumentPage !== 'function') {
  throw new Error('本教程需要 2.0.0 的正文分页接口，请按安装页核对 npm ls。');
}
for (const name of ['retrieveCapabilities', 'queryKnowledge', 'queryRuntime']) {
  if (name in CapabilityGraph.prototype) throw new Error('请安装与本文一致的 2.0.0 包');
}
console.log(typeof CapabilityGraph.open); // function
```

```sh
node check.mjs
```

预期输出是 `function`。这证明包入口和本教程所需的新接口存在；下一页创建 Provider 并成功调用 `open()` 后，才证明定义和加载配置有效。使用 `.mjs` 不需要 TypeScript 编译器。

## 安装内容

主包包含Core、TypeScript类型、文件Authority、本地与正式HTTP Reader、共享12查询工具、独立stdio/HTTP服务及CLI。根、`/mcp`、`/mcp/server`、`/readers/http`四个ESM入口各自提供类型；根SDK导入不启动服务或注册配置。

运行依赖固定server/node/client2.0.0、Ajv8.17.1、toml-eslint-parser0.10.1，以及语言校验的bcp-47和language-subtag-registry。自有SDK宿主显式声明自己使用的SDK。数据库、向量存储、RAG与VextJS执行由相应宿主或独立模块提供。

正常直接全局安装新增CLI时会注册stdio并关闭临时协议探针，不启动常驻HTTP服务；本地/依赖安装、ignore-scripts或无法证明直接目标时跳过自动接入。完整配置、手动register和卸载步骤见[MCP与CLI接入](../integrations/mcp-and-cli)。先确认本次制品包含这些子入口；已发布旧包不会因本地源码变化获得新能力。

## 常见问题

| 现象 | 检查 |
|---|---|
| `ERR_MODULE_NOT_FOUND` | 在运行脚本所属项目安装依赖，确认包名和当前工作目录 |
| `Cannot use import statement outside a module` | 使用 `.mjs`，或在所属 `package.json` 配置 `type: module` |
| Node 版本不满足要求 | 先用 `node --version` 检查上述范围；npm 的 engines 警告不等于运行兼容 |
| npm 返回版本或包不存在 | 用 `npm config get registry` 检查 registry 配置，再用 `npm view @devcodex/capability-graph version` 核对镜像是否已同步 |

安装后可用 `npm ls @devcodex/capability-graph` 查看项目实际使用的版本；1.0.0 不具备后文的 Selection 与多文档 Specification 接口。

## 从 1.1.0 升级到 2.0.0

2.0 聚焦静态能力图谱与文档原文访问，删除以下接口和配置。这些是破坏性变化，已有消费者可继续固定 1.1.0，或完成迁移再升级。

| 移除内容 | 调整方式 |
|---|---|
| 数据库 Authority / DatabaseAuthorityAdapter / DatabaseReadView | 由宿主导出正式 JSON 定义，使用 file Authority；不再配置数据库 view |
| retrieveCapabilities / CapabilityRetriever / DiscoveryAdapter | 使用 listCatalog 的结构化过滤或明确 ID；自然语言召回由独立模块负责 |
| queryKnowledge / KnowledgeRetriever / 索引证据、目标、命中与 invalidate 合同 | 使用文档引用和分页接口取得原文，RAG 由独立模块负责 |
| queryRuntime / RuntimeAdapter / 实例、观察、运行修订和兼容状态 | 由宿主自己的业务状态接口处理 |
| runtimeAdapters / knowledgeRetriever / capabilityRetriever | 删除这些配置字段；提供 undefined 也明确失败 |
| budgets.runtime / budgets.queryKnowledge / budgets.retrieveCapabilities | 删除已移除操作的预算分组 |
| CurrentCapabilityView.runtime / 专属错误、未使用的 CG_TIMEOUT 和 use_retrieval / reduce_document 动作 | 更新结果投影及错误分支，不保留空方法兼容层 |

Provider Schema、能力 ID、四种关系与八种正反查询、requires 闭包、Collection/Specification、directory/legacy 布局、scope 和 reload 继续保留。旧主版本游标请重新开始。文件根与文档来源身份不因产品范围调整而改名。

Provider 内外目录、node_modules 与 URL Reader 都继续支持。文档总大小没有准入上限；单页/全文/JSON/缓存预算分别管理资源。这里的分页取得原文，不建立索引或生成回答。后续独立 RAG 可通过公开能力身份与文档接口接入，目前没有单独发布的替代包。

完整变更见 [2.0.0 迁移清单](https://github.com/devcodex-labs/capability-graph/blob/main/changelogs/2.0.0.md)。旧链接已指向此说明；1.1.0 的完整实现保存在历史 tag。

## 历史：从 1.0.1 升级到 1.1.0

<a id="从-101-升级到-110" />

已有 `*.capability.json` 定义与旧相对路径可以继续使用，无需批量改名。新功能按需启用：

| 变化 | 升级方案 | 验证 |
|---|---|---|
| directory 布局 | 文件移入 `capabilities/**/*.json`，并显式设置 `definitionLayout: 'directory'`；缺省仍是 legacy | Catalog 身份与数量一致，不留下目录外的旧定义 |
| 外部目录 / node_modules | 在每个 Provider 配置 `knowledgeRoots`，locator 的 `root` 引用该 Provider 别名 | 实际读取原文；包中缺失章节另用目录或 URL |
| 大文档分页 | 使用 `readDocumentPage` / `readSpecificationPage`，保留 `nextCursor` 与修订 | 连续偏移与拼接字节一致；内容变更拒绝旧游标 |
| 全文与分页预算 | `read.maxBytes` 仍限制全文单篇返回，默认 32768；新增 `read.maxPageBytes` 独立限制分页/流块，默认也为 32768 | 原有显式全文预算继续生效；减小全文预算不缩小分页 |
| 输入与 JSON 预算 | 默认 selected 32、每维过滤 128、文档 8、整次 JSON 4 MiB | 拆批或按业务覆盖预算；检查逐项错误与查询级错误 |
| 外部 Retriever / 数据库 Adapter | 提供真实来源 Reader、完整证据与八类关系；更新后显式失效/重建索引 | 零命中也核验来源；过期索引明确失败 |

文档总大小没有准入上限。全文超出单篇预算时不会截断返回；改用分页即可完整续读。先锁定依赖版本和来源，再用[最小 Provider](./first-provider)及你实际使用的 Adapter 重测。

## 历史：从 1.0.0 迁移到 1.0.1

<a id="从-100-迁移到-101" />

这次升级包含破坏性 Schema 变化，**没有双 Schema 兼容层**。即使依赖写的是 `^1.0.0`，npm 也可能安装到 1.0.1；升级前核对 lockfile、备份定义，并在隔离项目中重测。仅锁定旧修订不能让旧定义变成兼容配置。

旧配置片段（仅用于识别，不能在 1.0.1 加载）：

```json title="migration-old-specification.json"
{
  "specification": {
    "specificationId": "acme.http.conventions",
    "version": "1",
    "entryRef": {
      "kind": "document",
      "knowledgeId": "SPEC-01",
      "locator": { "type": "relative-file", "path": "PROVIDER.md" }
    }
  }
}
```

新配置片段，替换 `provider.json` 中的 `specification`（Provider 的 `providerId/name/version` 保留）：

```json title="migration-new-specification.json"
{
  "specification": {
    "specificationId": "acme.http.conventions",
    "version": "1",
    "documents": [{
      "kind": "document",
      "knowledgeId": "SPEC-01",
      "role": "specification",
      "locator": { "type": "relative-file", "path": "PROVIDER.md" }
    }]
  }
}
```

| 迁移步骤 | 必须调整 | 如何验收 |
|---|---|---|
| 规范入口 | `entryRef` → 非空 `documents`；每篇 role 必须为 `specification` | 保存实际 PROVIDER.md；open 后 getProvider 显示 documentCount，显式 readSpecification 返回正文 |
| 能力知识 | 所有 Document、包括 Collection 成员补必填 `role`，如 `guide`/`example` | readDocuments 成功并能按角色过滤；缺 role 的旧声明预期 `CG_VALIDATION_FAILED` |
| 1.x 数据库 Adapter（历史范围） | 该接口在 2.0 已移除 | 升级到 2.0 时按本页清单导出文件定义 |
| 正向依赖 | 作者可声明 `requires`，不能在源定义写派生的 `requiredBy` | open 校验无环和端点；按需调用 resolveSelection 验证完整闭包 |
| 修订与消费者 | 哈希覆盖关系与文档映射变化，重新取得 Static Revision | TypeScript 重新编译；从新 Catalog 开始，重置旧游标/旧任务修订，不手写 provider.version 代替哈希 |

保留旧 `entryRef`、缺少 `role` 或写入源 `requiredBy` 都会明确校验失败。迁移后先跑[最小发现](./first-provider)，再核对你实际使用的知识、Selection 与 Adapter 路径；详见[完整 1.0.1 更新记录](https://github.com/devcodex-labs/capability-graph/blob/main/changelogs/1.0.1.md)。此说明不改变 npm 版本或重新发布包。
